# Cubase 8.0.40 multi-track regression: evidence-based isolation gate (2026-10-18)

## New user evidence after outputReady fix

The user confirms **no improvement whatsoever** after updating the ASIOOutputReady declaration to ASE_NotPresent. Thus changing outputReady was a legitimate contract correction but NOT a proven explanation of the real regression. Do not propose more speculative DLL replacements before targeted experiments.

Three stopped-session diagnostic samples (48kHz, 512 frames/block, requested 5ms, actual 480 frames =10ms):

| Session | callbacks | host silent blocks | host nonzero L/R blocks | max callback | over ASIO budget | WASAPI underrun | ASIO TimeInfo |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| A | 6417 | 6417 | 0 / 0 | 2472us | 0 | 0 | 1 |
| B | 5341 | 3488 | 1853 / 1853 | 17804us | 1 | 0 | 1 |
| C | 5 | 5 | 0 / 0 | 30us | 0 | 0 | 1 |

All three sessions had zero stream errors, zero producer failures, `last_hr=0`, and reported 2080 frames output latency (~43.33ms). The 5ms request was **not honored**: effective engine period stayed 480 frames (~10ms). Session B contained actual nonzero samples at the ASIO host output, so the bridge is not receiving exclusively zero data in all conditions. Session A had entirely zero-valued output *for its whole lifetime*, but the log has **no transport-play status**; this could simply be idle/silence. In session B silent blocks are an aggregate, and cannot be assumed to form a continuous 37s silent prefix. Do not make that inference.

### Proven boundaries

- PCM generated by the Cubase ASIO callback is classified immediately before ASIO planar-to-interleaved bridge. WASAPI underrun=0 means it received enough queued *frames*, **not** that the frames represent the expected musical passage.
- Each ASIO 512-frame block is 10.67ms; the ASIO producer queue target is 1024 frames, and the observed WASAPI buffer is 1056 frames. None explains an estimated 16-bar wrong-song-position at the output. At 120 BPM and 4/4, 16 bars is 32s, but project BPM/time-signature not known; treat as illustrative only.
- The code's `getLatencies` is **provisional** and changed from 1024 pre-start to 2080 after renderer initialized on the observed device. Such inconsistent host reporting deserves correction, but at 48k the difference is ~22ms, not 16 bars.
- The ASIO TimeInfo `systemTime` is currently derived from callback-time QueryPerformanceCounter rather than being correlated to the physical device frame that is represented by the advertised samplePosition. The user-owned original ASIOGLLD static analysis (`docs/BATCH11_PCM_CLOCK.md`, `docs/ASIO_CALLBACK_PIPELINE.md`) reconstructs a device-clock sample/time correction, using timeGetTime / IAudioClock paths. These are **credible clock-contract differences**, not proof they cause the symptom. Do not rewrite timestamp sources without an isolation test.
- The manual mini-host's steady 440Hz output does **not** exercise Cubase ASIO-Guard, offline/preprocessed tracks, plugin delay compensation or project seeking.

### Minimum diagnostic experiment — NO BUILD required

**Test A: ASIO-Guard OFF only (current TimeInfo stays ON).**

1. Make a duplicate of the Cubase project, remember its tempo and ASIO-Guard setting.
2. Cubase 8: Devices > Device Setup > VST Audio System. Disable ASIO-Guard and Apply; if it reloads driver or Cubase asks, close and restart.
3. Leave Modern Shared Audio selected. Run identical one-track and many-track passages, seek playhead to bar 0 and listen. Note: audible 16-bar source displacement? Serum? Track-count-dependent offset?
4. Restore ASIO-Guard after the test unless testing B.

**Test B: ASIO TimeInfo OFF only (ASIO-Guard returned to original ON setting).**

1. CLOSE Cubase completely; do not rebuild or re-register.
2. Normal PowerShell:

```powershell
New-Item -Path 'HKCU:\Software\ModernSharedASIO' -Force | Out-Null
New-ItemProperty -Path 'HKCU:\Software\ModernSharedASIO' -Name DisableTimeInfo -PropertyType DWord -Value 1 -Force | Out-Null
```

3. Reopen Cubase, same project and start position. After test, close Cubase, inspect last `ASIO_STOP ... asio_time_info=0 disable_time_info=1` log, and undo the override:

```powershell
Remove-ItemProperty -Path 'HKCU:\Software\ModernSharedASIO' -Name DisableTimeInfo -ErrorAction SilentlyContinue
```

4. If either independent test affects the failure, that isolates a concrete compatibility surface; compare outcomes before modifying driver source. **Do not disable ASIO-Guard and TimeInfo simultaneously in the first pass**, which would destroy causal information.

### Next engineering gate

If both experiments fail, instrument host callback timeline and audio-content arrival at block granularity, plus pair each ASIO reported sample position/time with IAudioClock/QPC physical device observations; add a deterministic multitrack seek-stress mock-host test. Track one audible marker at a known bar in the project, and distinguish: Cubase output buffer contains future audio vs output buffer correctly matches timeline but later PCM is reordered. Only then implement a targeted fix; no uncontrolled latency/period tweaks.
